This is the canonical release-status record for the product. A feature is not release-ready merely because its code exists. Each journey is tracked separately through code, database migration, deployment, feature-switch state, device testing, and field-pilot evidence.

## Status key

- **Code:** implementation present on the recorded GitHub revision.
- **Migration:** schema/seed migration applied to the connected Supabase project, not just committed.
- **Deployment:** evidence available from the Vercel or Supabase connection. A GitHub check is not proof of every user-facing alias or configuration.
- **Switch:** live Supabase `feature_flags` value at the snapshot; a missing switch defaults off in the app.
- **Device test:** recorded real-device result. Automated tests and APK builds do not count as a handset pass.
- **Field pilot:** evidence of use with real farmers/providers. Database rows alone do not establish that records came from a field pilot.

2. Review and apply the four pending November migrations through the normal reviewed migration workflow; then confirm the deployed function/schema versions and flags.
3. Reconcile `ai_photo_diagnosis=ON` with the agronomy review gate. Keep advice claims and photo diagnosis behind a verified, tested release decision.
4. Run and record real-device journeys on supported Android devices and weak connectivity, including OTP, farm entry, hiring GPS/proof, checkout, order/job disputes, and retry behavior.
5. Record pilot provenance and outcomes: distinguish seeded/demo/test records from real users and jobs, then track completion, disputes, repeats, and support interventions.
6. Re-run Supabase security/performance advisors after the migration and document disposition of each release-relevant finding.
