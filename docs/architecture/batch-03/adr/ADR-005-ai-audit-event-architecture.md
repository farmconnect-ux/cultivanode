# ADR-005: AI Audit Event Architecture

**Status:** Proposed — Independent Review Remediation (Batch 03.0) | **Date:** 2026-11-19

## Context
1. Granting `EXECUTE` on a general AI audit writer to `authenticated` allows clients to fabricate AI executions or guardrail results via PostgREST RPC.
2. In Supabase (`xdbqndgwisshhjqqksbe` verified), `service_role` has `rolbypassrls = true` and `rolsuper = false`, while `postgres` owns schema objects (`rolsuper = false`, `rolcreaterole = true`, `rolbypassrls = true`). Table-level `REVOKE` from `service_role` blocks direct table access because `service_role` is neither superuser nor table owner. However, granting `service_role` direct `EXECUTE` on `private.lookup_ai_actor_subject` still permits repeated bulk enumeration.
3. Because `postgres` can be used for both `pg_cron` jobs and manual administrative/migration SQL sessions, PostgreSQL cannot distinguish those sessions solely by the `postgres` role.
4. Because `apps/web` server modules share `SUPABASE_SECRET_KEY` (`service_role`), PostgreSQL cannot distinguish one Next.js server module from another at the database role level.

## Decision

### 1. Scheduled-Job Identity Assurance Model (`actor_kind = 'system'`)
**"Restricted privileged scheduler execution boundary, pending dedicated scheduler identity verification."**
- **A. Proposed Controls:** Scheduled wrappers in `private.*` have **`REVOKE ALL FROM PUBLIC, anon, authenticated, service_role`**. Job registration in `cron.job` (`pg_cron` `1.6.4`) and `private.ai_scheduled_jobs(job_name text PK, system_principal text UNIQUE NOT NULL, allowed_event_kinds text[] NOT NULL, is_enabled boolean NOT NULL)` is restricted to `postgres`. The wrapper validates `job_name`, `allowed_event_kinds`, and `is_enabled = true`, enforces `(job_name, run_window)` retry idempotency (`ON CONFLICT DO NOTHING`), fails closed for disabled/unregistered jobs, and rejects `anon`, `authenticated`, `authenticator`, and `service_role` callers.
- **B. Remaining Identity Limitation:** A manually initiated SQL session using `postgres` shares the same role as `pg_cron`; therefore, the current design does **not** constitute independently verified proof of `pg_cron` execution over manual `postgres` DBA sessions.
- **C. Batch 03.3 Staging Verification:** Test creating a dedicated non-`BYPASSRLS` role (`cultivanode_scheduler`) and assigning it via `cron.alter_job` on `CultivaNode-Staging`. If Supabase Hosted blocks custom `pg_cron` execution roles, document the `postgres`-only `private.*` wrapper (`service_role` revoked) + allowlist + idempotency as the strongest feasible boundary.

### 2. Enforceable `private.ai_actor_directory` Privilege Boundaries & Compliance Lookup
- **Table Boundary (`owner: postgres`, `private` schema, RLS enabled):** **`REVOKE ALL ON TABLE private.ai_actor_directory FROM PUBLIC, anon, authenticated, service_role`**. Because `service_role` has `rolsuper = false` and is not table owner, `BYPASSRLS` does not override table-level `REVOKE`.
- **Internal-Only Functions (`OWNER TO postgres`, `SECURITY DEFINER`, `SET search_path = ''`, `REVOKE ALL FROM PUBLIC, anon, authenticated, service_role`):**
  1. `private.resolve_or_create_ai_actor(p_profile_id uuid)`: callable only internally by `postgres`-owned audit-writer functions; rejects `deleted_at IS NOT NULL`.
  2. `private.anonymise_ai_actor(p_profile_id uuid)`: callable only internally inside `public.execute_account_deletion(uuid, text)`; idempotently sets `profile_id = NULL, deleted_at = COALESCE(deleted_at, now())`; cannot create or reactivate mappings.
  3. `private.lookup_ai_actor_subject(p_actor_subject_id uuid)`: **revoked from `service_role`, `authenticated`, `anon`, and `PUBLIC`** (no direct `service_role` enumeration).
- **Narrowly Scoped Compliance Lookup (`public.compliance_lookup_ai_actor(p_actor_subject_id uuid, p_purpose text)`):** `OWNER TO postgres`, `SECURITY DEFINER`, `SET search_path = ''`, `REVOKE ALL FROM PUBLIC, anon`, `GRANT EXECUTE TO authenticated`. A single-row response alone does **not** prevent enumeration; therefore the function enforces database-level, concurrency-safe anti-enumeration controls:
  - **Permission & Identity:** Requires `public.has_permission('audit.read')`, `private.account_active(auth.uid())`, and validated non-empty `p_purpose`; returns only the minimum compliance fields (`actor_subject_id`, `actor_kind`, `profile_id`, `deleted_at`) for the requested subject.
  - **Rate-Limit Identity & Scope:** Keyed to the **requesting compliance principal (`auth.uid()`)** (so rotating `p_actor_subject_id` cannot bypass the limit), plus a secondary **system-wide ceiling** across all compliance principals.
  - **Configurable Rolling Window & Provisional Thresholds:** Proposed configurable engineering defaults *(requiring security and operational review before production enforcement; not legally mandated)*: `15-minute` rolling window, max `10` lookup attempts per requesting principal, max `5` denied/unsuccessful attempts per principal, and max `30` system-wide attempts. Exceeding a threshold returns `throttled` (mapped to HTTP `429` with no actor data).
  - **Atomic Concurrency Enforcement:** Enforced inside PostgreSQL via `private.ai_compliance_lookup_limits` (`owner: postgres`, `REVOKE ALL FROM PUBLIC, anon, authenticated, service_role`) using `SELECT ... FOR UPDATE` / `pg_advisory_xact_lock` on `(scope_kind, scope_key)` so concurrent requests serialise before threshold evaluation and cannot race past the limit.
  - **Non-Recursive, Fail-Closed Auditing:** Every attempt (`permitted`, `denied`, `throttled`, `failed`) is recorded in `public.audit_log` (requesting principal, `p_actor_subject_id`, stated purpose, timestamp, outcome, optional `trace_id`; no unnecessary PII). Denied/throttled calls return a structured status record after inserting the `audit_log` row so PostgreSQL does not roll back the audit entry; audit-insert failures raise an exception and fail closed without returning actor data. Writing to `public.audit_log` avoids recursive dependencies on `private.ai_actor_directory`. *(Future implementation dependency: Batch 03.1/03.2 SQL + pgTAP verification.)*

### 3. Trusted AI Audit-Writer & Human Feedback Contract
- **General AI Audit Writer (`private.write_ai_audit_event(...)`):** `OWNER TO postgres`, `SECURITY DEFINER`, `SET search_path = ''`, `REVOKE ALL FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE TO service_role`.
- **Explicit `service_role` Limitation:** Isolating `private.write_ai_audit_event` invocations inside `apps/web/src/lib/ai-audit.ts` (called only after `auth.getUser()`, `account_active`, `can_view_farm`/`can_edit_farm`, and strict Zod/allowlist validation) is an **application-architecture and code-review boundary**, NOT an independently enforced database identity boundary, because all Next.js server modules share `SUPABASE_SECRET_KEY` (`service_role`). Provisioning a dedicated `ai_orchestrator` database role remains a future option if AI workloads are separated from the Next.js server.
- **Human Feedback Pathway (`public.record_ai_feedback(p_trace_id uuid, p_outcome text, p_note text)`):** `GRANT EXECUTE TO authenticated` (`PUBLIC, anon` revoked). Derives `auth.uid()`, checks `account_active` and `can_view_farm(farm_id)` for an existing `trace_id`, restricts `p_outcome IN ('accepted', 'rejected', 'modified')`, and cannot alter `provider`, `model_id`, `prompt_version`, `guardrail_result`, `actor_kind = 'system'`, or original execution outcome.
