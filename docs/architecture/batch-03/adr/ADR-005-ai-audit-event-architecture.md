# ADR-005: AI Audit Event Architecture

**Status:** Proposed — Final Security Boundary Clarifications (Batch 03.0) | **Date:** 2026-11-19

## Context
1. Granting `EXECUTE` on a general AI audit writer to `authenticated` allows clients to fabricate AI executions or guardrail results via PostgREST RPC.
2. In Supabase (`xdbqndgwisshhjqqksbe` verified), `service_role` has `rolbypassrls = true` and `rolsuper = false`, while `postgres` owns schema objects (`rolsuper = false`, `rolcreaterole = true`, `rolbypassrls = true`). Relying on RLS alone does not restrict `service_role`, whereas table-level `REVOKE` from `service_role` **does** block direct table access because `service_role` is neither superuser nor table owner.
3. An empty `request.jwt.claim.role` does **not** prove `pg_cron` execution (CLI/direct `postgres` sessions also lack HTTP JWT claims), and `current_user` inside `SECURITY DEFINER` is the function owner (`postgres`), not the caller.

## Decision

### 1. Verifiable PostgreSQL Scheduled-Job Identity (`actor_kind = 'system'`)
- **Registration Authority:** Only `postgres` (migrations / DBA) can register jobs in `cron.job` (`pg_cron` `1.6.4`) and `private.ai_scheduled_jobs(job_name text PK, system_principal text UNIQUE NOT NULL, allowed_event_kinds text[] NOT NULL, is_enabled boolean NOT NULL)`.
- **Execution & Privilege Boundary:** Scheduled AI wrappers in `private.*` have **`REVOKE ALL FROM PUBLIC, anon, authenticated, service_role`** — only `postgres` (which `pg_cron` uses in existing migrations `20260929090000` / `20261002095258`) or a dedicated non-`BYPASSRLS` role `cultivanode_scheduler` *(subject to Staging `cron.alter_job` verification in Batch 03.3)* can execute them. Because `service_role` is revoked, no HTTP server holding `SUPABASE_SECRET_KEY` can invoke the `pg_cron` system-event pathway.
- **Validation & Idempotency:** The wrapper verifies `session_user` / `current_setting('role', true)` is not `anon`, `authenticated`, `authenticator`, or `service_role`; validates `job_name` against `private.ai_scheduled_jobs` (`is_enabled = true`) and `cron.job` (`active = true`); restricts `event_kind = ANY(allowed_event_kinds)`; and enforces `(job_name, run_window)` idempotency (`ON CONFLICT DO NOTHING`) so retries do not duplicate audit rows.
- **Documented Limitation:** Any direct `postgres` admin/migration SQL session shares the `postgres` role with `pg_cron` unless `cultivanode_scheduler` is supported and configured; however, all `anon`, `authenticated`, and `service_role` callers are strictly blocked.

### 2. Enforceable `private.ai_actor_directory` Privilege Boundaries
- **Schema & Table Ownership:** `private.ai_actor_directory` is owned by `postgres` in the `private` schema (owned by `postgres`, excluded from PostgREST). RLS is enabled, and **all table-level grants (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) are revoked from `PUBLIC`, `anon`, `authenticated`, AND `service_role`**. Because `service_role` is neither superuser nor table owner, it cannot query or mutate `private.ai_actor_directory` directly.
- **Three-Function Interface (`OWNER TO postgres`, `SECURITY DEFINER`, `SET search_path = ''`, fully qualified refs):**
  1. `private.resolve_or_create_ai_actor(p_profile_id uuid)`: `REVOKE ALL FROM PUBLIC, anon, authenticated, service_role` — callable **only** internally by `postgres`-owned audit-writer functions; rejects `deleted_at IS NOT NULL` mappings.
  2. `private.anonymise_ai_actor(p_profile_id uuid)`: `REVOKE ALL FROM PUBLIC, anon, authenticated, service_role` — callable **only** internally inside `public.execute_account_deletion(uuid, text)`; idempotently sets `profile_id = NULL, deleted_at = COALESCE(deleted_at, now())`; cannot create or reactivate mappings.
  3. `private.lookup_ai_actor_subject(p_actor_subject_id uuid)`: `REVOKE ALL FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE TO service_role` (or compliance RPC gated by `has_permission('audit.read')`) — single-row lookup only; bulk enumeration prohibited.
- **`public.ai_audit_events`:** Strictly append-only (`private.forbid_change()`), storing opaque `actor_subject_id`, never mutated during account deletion.

### 3. Trusted AI Audit-Writer & Human Feedback Contract
- **General AI Audit Writer (`private.write_ai_audit_event(...)`):** `OWNER TO postgres`, `SECURITY DEFINER`, `SET search_path = ''`, `REVOKE ALL FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE TO service_role`. Accepts only allowlisted `event_type`s, validated `provider`, resolved `model_id`, `prompt_version`, `trace_id`, and `guardrail_result`, and verifies `p_actor_profile_id` has farm access (`can_view_farm`-equivalent) before calling `private.resolve_or_create_ai_actor`. Audit-write failures fail closed for actionable/state-changing flows.
- **Supabase `service_role` Limitation & Mitigation:** Postgres cannot distinguish two Next.js server modules sharing the same `service_role` key. Preventing unrelated server routes from calling `private.write_ai_audit_event` is an **application-architecture boundary** (isolated to `apps/web/src/lib/ai-audit.ts`), unless a dedicated `ai_orchestrator` DB role is provisioned in a future multi-service split.
- **Human Feedback Pathway (`public.record_ai_feedback(p_trace_id uuid, p_outcome text, p_note text)`):** `SECURITY DEFINER`, `SET search_path = ''`, `REVOKE ALL FROM PUBLIC, anon`, `GRANT EXECUTE TO authenticated`. Derives `auth.uid()`, checks `private.account_active(auth.uid())`, verifies `p_trace_id` exists on a farm where `private.can_view_farm(farm_id)` is true, restricts `p_outcome IN ('accepted', 'rejected', 'modified')`, and appends a child feedback row (`parent_event_id`) without permitting any modification of `provider`, `model_id`, `prompt_version`, `guardrail_result`, `actor_kind = 'system'`, or original execution outcome.
